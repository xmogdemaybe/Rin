# Что добавлено в этом форке (Rin)

Данный репозиторий представляет собой форк [fenixvd/Raine](https://github.com/fenixvd/Raine) (который, в свою очередь, является портом на Java C++ проекта [Alex2772/kuni](https://github.com/Alex2772/kuni)). В этом документе зафиксированы ключевые технические отличия, оптимизации, архитектурные модули и исправления безопасности, отсутствующие в базовом апстриме.

Архитектура системы описана в [architecture.md](architecture.md), базовые возможности персонажа — в [features.md](features.md).

---

## 1. Реестр доверия (`TrustLedger`)

* **Формат хранения:** Реестр хранится в `data/trust.md` (одна запись на пользователя: `username/first_name: level - id`). Изменение инициируется моделью через инструмент `note_trust`. Доступ к файловой системе для LLM закрыт: сериализацию, валидацию и форматирование выполняет бэкенд.
* **Защита от Prompt Injection:** Имя пользователя и комментарий экранируются через парсер разметки до записи на диск. Служебные теги (например, `</your_trust>`) нейтрализуются, предотвращая выход из контекстной секции.
* **Инвариант владельца:** Запись владельца зафиксирована статически в системном промпте. Вызов `note_trust` по ID владельца завершается отказом на уровне валидатора.
* **Лимиты и квоты:** В системный контекст передаётся не более 40 строк реестра. Кулдаун на изменение уровня доверия одного и того же аккаунта — 6 часов.
* **Конфигурация:** Тумблер `trust_ledger_enabled` (`true`/`false`).

## 2. Развитие личности (`CharacterGrowth`)

* **Дневной сбор сигналов:** Инструмент `record_trait_signal` фиксирует устойчивые паттерны поведения модели. Сигналы агрегируются в метаданных сессии дневника без выделения дополнительной БД.
* **Ночная консолидация:** Фоновый процесс анализирует собранные за сутки сигналы и атомарно перезаписывает `prompts/character_growth.md`. Если ответ модели пуст, содержит синтаксический мусор или превышает лимит токенов, шаг отменяется с сохранением предыдущей версии файла.
* **Структура черты:** Фиксированный формат из 3 полей: `категория`, `формулировка от 1-го лица`, `дата фиксации`. Категории строго типизированы: `identity`, `personality`, `preference`, `interest`, `guideline`, `experience`.
* **Правила верификации:** Черта закрепляется только при повторном подтверждении с интервалом не менее 12 часов либо при разовом коэффициенте уверенности $\ge 0.9$. Сигналы без повторного подтверждения экспайрятся через 14 дней.
* **Лимиты выборки:** За один проход консолидируется не более 30 групп черт; размер итогового промпта ограничен 40 строками.
* **Конфигурация:** Тумблер `character_growth_enabled` (по умолчанию `false`).

## 3. Спонтанные действия и ночной режим (`NightSleep`)

* **Инициативные сообщения:** Реализована отправка вечерних прощаний и утренних приветствий без входящего триггера. Вероятность срабатывания рассчитывается пропорционально уровню доверия: для владельца — $0.8$, для доверенных контактов — до $0.5$.
* **Кулдауны:** Минимальный интервал между спонтанными обращениями к одному пользователю — 14 дней. Таймеры утренних и вечерних триггеров независимы.
* **Детекция активности (Smart Deferral):** Перед переходом в ночной режим проверяется состояние очереди: при наличии непрочитанных сообщений или активности в диалоге менее 10 минут назад отбой откладывается (максимальное время ожидания — 90 минут, после чего бот принудительно засыпает).
* **Конфигурация:** `night_sleep` (`true`/`false`).

## 4. Мультимодальный пайплайн Telegram Stories

* **Парсинг структуры:** Истории обрабатываются как составные объекты TDLib (`TdApi.StoryContent`): извлекаются медиафайл, подпись и интерактивные зоны (`StoryArea`: ссылки, геопозиция, реакции, погода). Текст подписи изолируется в теги `<story_caption>` во избежание спуфинга системных инструкций.
* **Лента историй (`view_stories`):** Список активных историй агрегируется из событий TDLib в памяти. Тулза возвращает компактный индекс контактов с количеством непросмотренных публикаций и автоматически разбирает до 2 самых свежих историй. Инкремент счётчика лимита происходит **до** сетевого запроса, что исключает циклический перебор всей ленты при сетевых сбоях.
* **Точечный просмотр с вопросом (`watch_story`):** Вызов с параметром `question` инициирует повторный анализ кадра/ролика с фокусом на конкретную деталь в обход дискового кэша, предотвращая перезапись общего описания частным ответом. Если модуль зрения отключён, тулза явно возвращает статус игнорирования вопроса.
* **Кэширование и видеодекодер:**
  * Проверка дискового кэша вынесена **до** распаковки кадров.
  * Видео разбивается на ключевые кадры через встроенный `jcodec` (до 16 кадров с шагом $\ge 1$ сек).
  * Аудиодорожка извлекается и передаётся в STT только при фактическом наличии звукового потока.
  * Запись кэша на диск выполняется строго атомарно (`AtomicFiles.writeString` через `.tmp` и `ATOMIC_MOVE`).
  * **Фоллбэк на заставку:** если ролик посмотреть не удалось (зрение выключено, кадр не скачан, декодер не потянул), в контекст уходит единственный кадр — и в открывающем теге он помечен `preview="true"`. Догадка по одной картинке не должна читаться как просмотренный ролик.
* **Публикация историй (`post_story`):** По умолчанию отключена (`stories_posting=false`). Проверяет права аккаунта в TDLib перед выполнением, принимает файлы исключительно из внутренней директории бота и поддерживает таргетинг аудитории через `stories_audience` (`contacts`, `everyone`, `close_friends`). Лишняя проверка физической камеры в рантайме устранена.

## 5. Аудио и распознавание речи (`ModelHearing`)

* **Атомарный захват слота обработки:** Регистрация задачи (`claim`) выполняется строго после успешной валидации и чтения аудиофайла (`soundOf`), исключая блокировку очереди при битых файлах.
* **Поллинг Telegram STT:** В `Telegram.recognizeSpeech` добавлен корректный парсинг состояний TDLib: цикл поллинга мгновенно прерывается при получении `SpeechRecognitionResultError`, не расходуя 30-секундный таймаут. Запрос состояния сообщения выполняется в обход `ShortLivedCache`, устраняя 15-секундную задержку на чтение устаревшего статуса.
* **Отметка «прослушано» не мгновенно:** `hearing_mark_listened` (по умолчанию `true`) решает, ставить ли её вовсе — галочку увидит автор сообщения, и решать должен владелец. `mark_heard_delay_seconds` (по умолчанию `4`) задаёт минимальную паузу от начала разбора до отметки: запись слушают столько, сколько она звучит, и мгновенная галочка выдала бы, что её не слушали вовсе. В `read_only` задержка обнуляется — до Telegram отметка всё равно не доходит, а ждать незачем. Повторный разбор того же вложения отметку не дублирует: помеченные сообщения держат в памяти одного хода.
* **Нормализация и фильтрация тишины:**
  * Ответы модели вида `No speech detected.`, `silence`, а также системные комментарии в квадратных скобках `[...]` распознаются как отсутствие речи и не сохраняются в постоянный кэш.
  * Пустые файлы кэша (0 байт) считаются промахом (`cache miss`) и инициируют повторный разбор.
* **Лимиты длительности аудио:**
  * Аудиопотоки длиннее 90 секунд принудительно обрезаются до лимита бюджета токенов с добавлением мета-тега `[предразбор: обрезано до 90 с]`.
  * Лимит длительности передаётся в `VideoAudio` до старта демуксирования.
* **Надежность декодеров:** В `OggOpusReader` добавлена проверка версии заголовка по RFC 7845 и отсечение нулевых сегментов таблицы пакетов. В цикле декодирования AAC проверяется флаг прерывания потока (`Thread.interrupted()`), а дескриптор `FileChannel` гарантированно закрывается в блоке `finally`.

## 6. Отказоустойчивая память и дневник

* **Гибридный поиск:** Помимо векторного поиска реализован полнотекстовый лексический фоллбэк без учета однобуквенных токенов на случай сбоев эндпоинта эмбеддингов.
* **Неблокирующий доступ:** Тяжёлые вычисления векторов и дисковый ввод-вывод вынесены за пределы синхронизированных блоков (под блокировкой создаётся только in-memory снимок коллекции).
* **Смысловая кластеризация при консолидации:** Записи объединяются на основе косинусного сходства (порог $\ge 0.5$, не более 6 записей в группу), предотвращая склейку несвязанных фрагментов в один блок.
* **Дедупликация триггеров:** Сохраняется кольцевой буфер из 8 последних использованных воспоминаний для предотвращения зацикливания спонтанных реплик вокруг одного события.

## 7. Сетевой стек и сетевая изоляция

* **Ранняя инициализация MTProto / SOCKS5:** Параметры прокси регистрируются в TDLib до запуска процедуры авторизации через нативный вызов клиента, что обеспечивает прохождение SMS/кодов подтверждения в изолированных сетях. Поддерживается парсинг параметров напрямую из `t.me/proxy` URL.
* **Раздельная маршрутизация (`llm_proxy`):** Трафик к Telegram API и трафик к LLM-провайдерам разведены по независимым конфигурациям (Telegram может работать через прямой интерфейс/MTProto, а модель — через локальный HTTP/SOCKS5 прокси).

## 8. Безопасность контекста и санитизация

* **Экранирование чужого текста (`phone.Markup`):** Тексты сообщений, имена отправителей, названия чатов, подписи к вложениям, описания ссылок, сниппеты веб-поиска и расшифровки голоса проходят через общий шлюз перед вставкой в разметку промпта. Открывающая скобка перед буквой или слэшем нейтрализуется, значения атрибутов дополнительно теряют кавычки и переводы строк. Внутренний маркер `raine_internal_low_quality`, присланный собеседником, заменяется на `malicious`.
* **Сокращение ошибок (`core.ErrorNote`):** Тело чужого ответа не попадает в контекст целиком: наружу уходит одна строка не длиннее 200 символов без управляющих символов и разметки. Значения при `api_key`, `token`, `secret`, `authorization`, `password` и `cookie` и длинные base64-подобные последовательности заменяются на `[скрыто]`. Необработанное исключение инструмента превращается в системный маркер `NOTHING_WORKED`; сырой текст ошибки остаётся во внутреннем журнале.
* **Безопасный режим (`read_only=true`):** Инструменты с пометкой `mutating` (`send_telegram_message`, `forward_message`, `post_to_channel`, `post_story`, `remove_message`, `take_photo` и другие) не попадают в `Toolbox`: право на действия встроено в сам набор, а не во внешнюю обёртку. Низкоуровневые методы `TelegramActions.ReadOnly` выбрасывают `IllegalStateException` вместо возврата фиктивного нуля, поэтому отказ виден сразу, а не выглядит успехом.

## 9. Адаптация под Gemini API

* **Чистое тело запроса:** Тело собирается вручную из `model`, `messages` и `tools`, поэтому специфичные для сторонних прокси поля (включая `session_id`), вызывающие `HTTP 400` в Google AI Studio, в него не попадают.
* **Подписи размышлений:** `thought_signature` хранится не по строковому id вызова, а по конкретному объекту `ToolCall` и привязана к модели и к тому, основная она или резервная: одинаковый id у двух моделей больше не путает подписи. Кэш ограничен 256 записями; для импортированной истории без подписи подставляется официальный маркер `skip_thought_signature_validator`, а не чужая криптографическая подпись.
* **Контроль вызова инструментов:** При ожидании ответа тулзы клиент ставит `tool_choice=required`. Если шлюз отвечает `400` на принудительный вызов, запрос повторяется без `tool_choice`, а отказ запоминается отдельно для основной и резервной модели, чтобы не переспрашивать на каждом ходе.

## 10. Стабильность ядра и сборка

* **Потокобезопасный Rate Limiter:** Запросы к Telegram API защищены единым семафором с фиксацией временных окон под общим замком, что исключает всплески RPS при параллельной работе фоновых потоков и диалога.
* **Headless запуск через `installDist`:** Сборка боевого контура переведена на нативный скрипт дистрибутива Gradle (`./gradlew installDist` $\rightarrow$ `build/install/rin/bin/rin`). Запуск через фоновый `setsid` исключает внезапное завершение процесса при сбое демона сборщика.
* **Тестовое покрытие:** Ветка стабилизирована на 834 unit-тестах в окружении WSL2 (`Ubuntu-26.04`), моков нет — клиентов модели подменяют лямбдами и скриптованными ответами. Каждое поведенческое изменение проходит TDD «красное → зелёное» и мутационный прогон: в стенд вносится одна строка-поломка, и предсказанный набор тестов обязан на неё упасть (для изоляции памяти — группы по 12, 14, 7 и 8 мутаций, все пойманы).

## 11. Публикация в каналы и пересылка

* **Публикация в канал (`post_to_channel`):** За флагом `channels_posting_enabled` (по умолчанию `false`). Тулза появляется только при открытии существующего канала и публикует один текстовый пост до 4096 символов UTF-16; создавать каналы и отправлять медиа она не умеет. Перед отправкой заново проверяются тип чата и `Lockdown`, а в безопасном режиме тулзы нет вовсе. Ответ различает подтверждённую публикацию (`message_id`), отказ, принятие без подтверждения и неизвестный исход; в двух последних случаях модель прямо просят проверить канал и не дублировать пост.
* **Честный статус пересылки (`forward_message`):** Telegram умеет переслать только часть связки, не вернув ошибки, поэтому `TelegramActions.forward` возвращает число реально доставленных сообщений. Ответ говорит, сколько дошло из запрошенного, и запрещает повторять пересылку вслепую; сбой комментария сообщается отдельно от уже принятой пересылки.
* **Круг общения с обеих сторон:** Перед пересылкой проверяются и исходный чат, и получатель — владелец может сузить круг на ходу, пока набор инструментов ещё жив. Пересылать можно только из чата, открытого в текущем контексте (`writingChatId`): тулза, оставшаяся от прошлого чата, отказывает и ничего не отправляет.

## 12. Резервная разговорная модель

* **Конфигурация:** `fallback_model` (пусто — резерва нет), `fallback_base_url` и `fallback_api_key` (пусто — наследуются адрес и ключ основной модели). Настройки читаются при запуске; при пустом резерве в журнал пишется предупреждение.
* **Триггер:** Только исчерпание квоты — HTTP `402`/`429` или явные коды `insufficient_quota`, `quota_exceeded`, `resource_exhausted`, `rate_limit_exceeded`, `insufficient_credits`, `insufficient_balance`. Ошибки `5xx`, включая пиковые `503`, и сетевые сбои остаются обычными повторными попытками основной модели: резерв не подменяет ретраи.
* **Границы:** Переключение действует внутри текущего вызова разговорной модели, следующий вызов снова начинает с основной. Эмбеддинги, зрение и слух резерв не используют. Ключи обеих моделей вырезаются из текста ошибок, а отказ по квоте не блокирует следующие ходы.
* **Совместимость:** У основной и резервной модели отдельно запоминаются поддержка `tool_choice` и подписей размышлений, поэтому резерв может быть шлюзом другого вендора.

## 13. Веб-поиск: форматы и честные ошибки

* **Оболочка ответа:** Принимаются оба известных формата — `{"results": [...]}` и `{"data": [...]}`. Наличие ключа `results` (даже со значением `null`) исключает откат к `data`: это не другой формат. Пустой массив означает честное «ничего не найдено», а `null`, не-массив или битый элемент — ошибку неизвестного формата.
* **Проверка до вывода:** Весь массив результатов проверяется на структуру (объект с текстовыми `title`, `url` и `content`) до формирования блока. Повреждение за пределом первых пяти результатов всё равно даёт ошибку, а не пустую находку.
* **Ограничения чужого текста:** Заголовок обрезается до 300 символов, эхо запроса — до 500, слишком длинный URL опускается целиком (обрезанный выглядит рабочим, но ведёт не туда). Сниппеты проходят через `Markup`, ключ API маскируется в тексте ошибки.

## 14. Изоляция памяти по доверию (`Audience`)

* **Метка источника у записи:** каждая страница дневника хранит в метаданных `source` (`owner_dm`, `private_dm`, `group`, `general`) и `source_chat`. Разговор, задевший несколько чатов, получает строжайшую метку из затронутых, она переживает начисление опыта, перезапуск и ночное сведение. Записи без метки (до этого форка) читаются как `general` — миграция файла не нужна.
* **Отсечка живёт в коде, а не в промпте:** попросить чужой секрет у модели можно теми же словами, что и свой, а различие видно только по числам, которые она сама должна была бы сопоставить со строками файла доверия. Решение принимает `Audience(chatId, trust, owner)`, которого считают на входе каждого хода.
* **Границы выдачи:** владелец видит всё; друг (`trust >= 1`) — всё, кроме лички владельца (она не открывается ни за какое доверие); случайный собеседник — только `general` и то, что было сказано в его же разговоре. Зритель без чата ни с чем не «совпадает»: `chatId = 0` у события вне переписки не открывает чужие лички. Если чата у уведомления нет вовсе, зрителем считается человек, о котором событие.
* **Опыт не утекает:** закрытую запись не списывают как вспомненную, поэтому `diary.use` к ней не обращается — иначе чужие секреты набирали бы сигналы от разговоров, где их не показывали.
* **Атрибуция внутри блока:** каждая выданная запись подписана строкой `[from: …]` о происхождении. Внешний тег блока не меняется: на него опирается вырезание подмешанного из пересказа, и без этого она начала бы вспоминать собственные воспоминания.
* **Средняя память:** `<things_to_remember>` с обещаниями, незакрытыми делами, настроением и состоянием тела подмешивается в системный промпт только владельцу и тем, кому доверие не ниже `1`. Постороннему не уходит ни строчки — этот текст задаёт тон каждому ответу и содержит имена людей, которые ему ничего не рассказывали.
* **Порывы:** поводом для спонтанного сообщения может стать только запись с меткой `general` — иначе сказанное в личке всплыло бы в первом попавшемся чате.
* **Обрыв сети:** дамп отложенного разговора хранит `source` и `source_chat`, поэтому пересказ, дописанный после рестарта, не «отмывается» в общее. Прежний голый список сообщений по-прежнему читается (как `general`).
* **Ночное сведение:** объединённая запись получает строжайшую метку исходных, а если эти исходные пришли из разных чатов, адрес ставится `0` — правдоподобный, но неверный чат был бы враньём.
* **Доверие как список доступа:** при `trust_ledger_enabled=false` из набора уходят инструмент `note_trust` и строка реестра в промпте, но `data/trust.md` код продолжает читать: иначе друзья за один тумблер превратились бы в рандомов с `trust = 0`.

## 15. Легенда разметки контекста

Всё, что бот показывает модели из чужих данных, завёрнуто в теги: разметку генерирует код, а не модель, и чужой текст внутри неё проходит через `Markup`.

| Разметка | Где | Что значит |
| --- | --- | --- |
| `<link url="…" chat="…" album="true">…</link>` | вложенным блоком в теле `<message>` | чужой пост по ссылке `t.me` раскрыт и показан прямо в сообщении. За один экран раскрывается не больше 3 ссылок, не больше 2 на сообщение, ответ кэшируется на час (промах — тоже ответ, чтобы битый адрес не долбил Telegram). Вложенный блок собирает выбросной форматтер: без зрения, правок и ссылок внутри ссылок. Не путать с `<link_preview>` — это превью, которое нарисовал сам сайт. |
| `<edited><was>…</was><now>…</now></edited>` | тело `<message>` | сообщение отредактировали, и прежние слова показаны рядом с новыми. Отсчётом служит её собственное чтение (память на 512 сообщений, сутки жизни): дифф выдают один раз, при последующих просмотрах остаётся только отметка. |
| `edited="true"` | атрибут `<message>` | правка была, но прежних слов не знать (сообщение отредактировали до первого чтения) либо перемены с прошлого показа нет. |
| `preview="true"` | атрибут открывающего тега описания вложения, например `<video description preview="true">` | это заставка одним кадром, а не просмотренный ролик: по одному кадру не узнать, что было дальше, и догадка не должна уходить в разговор как увиденное. |
| `reactions="(👍 by Аня;❤️ 5)"` | атрибут `<message>` | реакции под сообщением: до трёх авторов — по именам, дальше — числом; кастомный значок показан как `[custom]`, платные опущены. Отдельное событие о непрочитанных реакциях выбрасывает кэш имён, иначе список авторов залипал бы на 15 секунд. |
| `<your_diary_page additional_context just_for_reasoning no_plagiarism no_copy>` | контекст хода | страница дневника, подмешанная по близости; первой строкой внутри блока — `[from: …]`, если у записи есть происхождение. Длинное имя тега — маркер: по нему подмешанное вырезают из пересказа, который пишет модель. |
| `<memory_piece relatedness="…">` / `matched_by="words"` | ответ тулзы `ask` | находка подагента-поисковика; `matched_by="words"` означает, что сработал запасной лексический канал. |
| `<things_to_remember>` | системный промпт | средняя память: обещания, незакрытые дела, эмоциональное и физическое состояние. Только владельцу и `trust >= 1`. |
