# Правила для ИИ-кодера этого репозитория

Проект: «Rin» — юзербот на Java 25 (Gradle, Kotlin DSL), продолжение
форка Raine, который в свою очередь переписан из
[Alex2772/kuni](https://github.com/Alex2772/kuni). Устройство и запуск —
в [README.md](README.md) и `docs/`.

## Как работать

- После каждого изменения гнать полный набор тестов: `./gradlew test --no-daemon`.
  Новый код идёт в паре с новыми тестами; коммит зелёного состояния.
- Правки делаются маленькими: один пункт — своя ветка и свой pull request.
  Описание коммитов и комментарии в коде — по-русски; никаких обрывков
  чужих языков и случайных вставок.
- Тесты правятся вместе с кодом только когда изменился сам предмет проверки.
  Подгонять проверку под «зелёность» кода нельзя.

## Мелкая гигиена правок

- Файлы длиннее пары тысяч строк (`TelegramTools`, `NotificationLoop`,
  `RaineApp`) не читать целиком: сначала `rg` по нужному символу, потом
  кусок вокруг находки.
- Диф держать минимальным: не переотступать соседний код и не задевать
  строки рядом с правкой. Обёртка — ранний `return` или `if` вокруг, а
  не перестройка ветки.
- После любого слияния или ребейза считать его сломанным, пока не
  проверено: искать `<<<<<<<`, `=======`, `>>>>>>>` по всему дереву, а не
  только в `.java`.

## Git: шлюз разрешений

- Читать можно всё: `status`, `log`, `diff`, `show`, `blame` и `fetch`
  выполняются без спроса — они не меняют ни дерево, ни удалённый репозиторий.
- Мутирующее — `add`, `commit`, `merge`, `rebase`, `tag`, `push`, `stash`,
  удаление веток, — только по явной отмашке владельца на этот конкретный шаг.
  Разрешение на пуш не распространяется на следующий коммит; цепочку
  «коммит + пуш» не делать, пока не просят оба.
- Рабочая линия — приватный remote `rin`, ветка `main`. Публичный `fork` —
  только по прямому приказу, только в `master` и только после проверки, что в
  дельте нет значений из живого `config.properties`. `origin` и `upstream` —
  источники апстрима, не место для наших правок.
- Один логический шаг — один коммит. Ветка от `main`, вливание `--ff-only`,
  ветка после вливания удалена. Правка поведения начинается с падающего теста:
  красное → зелёное, иначе непонятно, что именно закрепил.
- Изменилось поведение — правка `docs/fork-features.md` едет в том же коммите,
  а не «потом отдельно». Документация, отставшая от кода, считается сломанной.
- Живая копия бота — не часть коммита: `config.properties`, живые `prompts/`
  и `data/` живут вне git, а пересборка рабочей копии — отдельная
  договорённость с владельцем, а не следствие пуша.

## Формат сообщения коммита

- Префикс обязателен и отражает суть результата: `[+]` — новая возможность,
  `[*]` — багфикс или смена поведения, `[-]` — что-то убрано, `[=]` —
  документация, тесты и рутина без смены поведения.
- Одна короткая человеческая строка: что стало видно или что перестало
  ломаться. Без стеков вызовов, без перечисления файлов, без пересказа диффа.
- Без `Co-Authored-By` и любых подписей ИИ.
- «fix», «update», «правки по ревью» и строка длиннее одной фразы — не
  сообщение коммита, а его отсутствие. Такие переписывать до отправки.

## Чего не трогать

- Секреты (`api_id`, `api_hash`, ключи моделей, MTProto-прокси) не коммитить
  и не показывать. Личное живёт вне git: `config.properties`, `data/`,
  `session/`, `prompts/`, `cache/`, `logs/`.
- Промпты править в `prompts-example/` — живые `prompts/` не коммитятся.
- Java-пакет `ru.rainedev.raine` и системные свойства `raine.*` не
  переименовывать: самая дорогая правка при нулевой видимой пользе.
- Бюджеты уже встроены и соблюдаются новым кодом: сон, лимиты ночной
  консолидации (`sleep_consolidation_max_requests/max_tokens`), антиповтор.
  Шансы, задержки между попытками и паузы после отказа — константы в коде
  по решению владельца, не заводить для них настройку.
- Не добавлять без явного запроса владельца: Docker, «официальный» Bot API
  вместо TDLib-юзербота, отдельные файлы-профили чужих ИИ-инструментов.
- Данные владельца (`data/`, `config.properties`) ни при каких правках
  не удалять и не переписывать тестами.
